## Mobile field console implementation

The user requested a modern cross-platform phone app for inspection, monitoring,
and control, with native optional. Implemented a Preact/TypeScript/Vite PWA in
`web/`, optional FastAPI adapter in `teach_and_find/mobile/`, and a synthetic
interactive robot adapter. Node is only a build dependency; production runs the
compiled app and API from the same Python host. No cloud publishing or live robot
connection was performed.

Delivered operator flows: pairing; camera/freshness/connection monitoring;
exclusive bounded hold-to-drive; release/STOP/blur/tab/disconnect locking;
reference upload/list/rename/archive/history; operator-annotated frame capture;
checklist creation/assessment; portable HTML/JSON/PNG report ZIP download. The
default synthetic demo explicitly seeds three objects with scripted evidence and
one pass/fail/unknown each. It does not claim automated perception or physical
movement. Search missions and third-person phone video remain unintegrated.

Core changes: project-owned `CameraFrame`; transport-independent `ControlGate`;
SQLite migration 3 for provenance; relay `M` frame protocol with camera/session,
sequence and local-age metadata; separate camera/command sockets; zero publication
on both ROS velocity topics; cleanup of owned relay sockets/threads. Legacy
`F`/`C` clients still work. Capture UTC is a conservative host estimate using ROS
header age, relay buffering, and full RTT; ROS clock assumptions need hardware
verification and this is not cross-device synchronization.

Meaningful regressions include stale/repeated commands, competing operators,
expired sessions, malformed control contracts, invalid/stale images, v2 database
migration preservation, monitor-only mode never opening a command path, and a
stop arriving while a nonzero transport send is in flight. Browser testing found
and fixed a duplicate HTTP/WebSocket stop race that could cancel a newly armed
session. The browser now uses one ordered stop channel with HTTP fallback when
the socket is unavailable. No motion is queued offline; reconnect stays locked.

Validation: `make check`; `make test` (**48 passed**, one upstream Starlette/httpx
deprecation warning); `make app-build` (TypeScript + Vite); `make app-test`
(**3 Chromium scenarios passed**, desktop and 390 px phone viewport); `make build`
(wheel and sdist with generated frontend assets). The browser suite uses a
temporary directory and loopback server, stops it on exit, and writes screenshots
to ignored `runs/mobile-preview/`. Desktop Monitor/Inspect and phone
Monitor/Control/Inspect screenshots were visually reviewed. Application JavaScript
is about 50 kB raw / 19 kB gzip excluding CSS/fonts, not a performance benchmark.

Entry point: `make app-setup`, `make app-build`, then `make app`; pair at
`http://127.0.0.1:8080` with the terminal code. For phone access use
`make app APP_ARGS="--host 0.0.0.0 --data-dir data/mobile-demo"`. HTTPS trusted by
the phone is needed for installable PWA/service-worker behavior on LAN. The
[app guide](../13-mobile-console.md) and
[architecture SVG](../diagrams/mobile-console.svg) document runtimes, contracts,
explicit relay selection, and remaining limits.

Next concrete step: inventory the actual Standard kit's ROS environment and
camera header clock, then run a supervised stationary camera/stop/latency trial
with an explicitly selected relay. Measure command units and stop behavior before
allowing motion. Real Android/iOS home-screen installation, Safari, Wi-Fi jitter,
hardware motion, battery/pose telemetry, GPU models, and Phone Observer calibration
were not tested. F06/F07 have software integration evidence; F28 remains partial
because autonomous search is not yet exposed by the app.
